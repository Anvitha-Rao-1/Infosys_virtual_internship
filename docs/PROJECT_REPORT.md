## A. The existing ML system

Three models already existed. **None of them was retrained, replaced or
duplicated** by this work.

### A1. Finance forecasting (Engine A)

| | |
|---|---|
| Files | `ml/forecasting.py`, `ml/train_model.py` |
| Type | Time-series regression |
| Candidates | Linear Regression (scikit-learn), ARIMA(1,1,1) (statsmodels), XGBoost (recursive, lag features) |
| How one is chosen | Backtest: hold out the last ~3 months, re-fit each candidate on everything before, score by MAE. Lowest MAE wins. |
| Fitted on | **Your own** monthly income & expense totals |
| Predicts | Next 3 months: income, expense, profit, profit margin, cumulative cash flow, plus a 95% confidence band |
| Output cached in | `forecast_cache` (JSON) |
| Read by | `analyse.php` → Finance tab |

### A2. Habit / productivity forecasting (Engine B)

Same three candidates and the same backtest, fitted on your own weekly
series, predicting 2 weeks ahead of:

- `completion_pct` = check-ins ÷ (active goals × 7) × 100
- `productivity_score` = **0.6 × completion_pct + 0.4 × time_pct**, where
  `time_pct` = minutes invested ÷ (active goals × avg `est_minutes` × 7)

Minutes come from real Focus Session timings where logged, otherwise from
each goal's self-reported `est_minutes`. The score formula is a **definition,
not a learned model** — the ML happens when it is forecast forward.

### A3. Burnout risk (Engine C)

| | |
|---|---|
| File | `ml/burnout_model.py`, artifact `ml/data/external/burnout_model.joblib` |
| Type | Binary classification |
| Model | `RandomForestClassifier` — 200 trees, max_depth 6, min_samples_leaf 20, `class_weight="balanced"` |
| Trained on | `modern_teen_mental_health_main.csv` — **30,000 rows**, 1,000 students |
| Label | `stress_level >= 7` on the dataset's 0–10 scale |
| Features (9) | sleep_hours, screen_time_hours, mood, journaled_today, meditated_today, exercised_today, social_interaction_rating, support_feeling, is_weekend |
| Measured performance | **accuracy 0.854, ROC-AUC 0.942**, confusion matrix `[[4296, 874], [0, 830]]` |
| Output cached in | `burnout_predictions` |

### ⚠️ A4. Two things about the training data you must state accurately

**1. The finance "Kaggle" dataset is synthetic.** `ml/data/README_DATASET.md`
says so in its own first line. The default benchmark
(`ml/data/finance_benchmark.csv`, 2,756 rows, Jan 2015 – Jun 2025) was
**generated by a script** with seed `np.random.default_rng(7)`. It has the
right *shape* — columns, date range, category mix, seasonal spikes — but it
is not public data.

A real Kaggle file *is* in the repo —
`ml/data/kaggle_raw_daily_household_transactions.csv`, 2,461 rows, columns
`Date, Mode, Category, Subcategory, Note, Amount, Income/Expense, Currency` —
but it is **not the default**; `DEFAULT_KAGGLE_PATH` points at the synthetic
one. You can switch with `python train_model.py --kaggle ml/data/kaggle_raw_daily_household_transactions.csv`.

Say: *"the burnout classifier is trained on a real 30,000-row external
dataset; the finance benchmark is a synthetic stand-in with the right shape,
and a real Kaggle transactions file is bundled as an alternative."*

**2. The burnout model is effectively a mood classifier.** Its own feature
importances:

| Feature | Importance |
|---|---|
| mood | **0.990** |
| sleep_hours | 0.003 |
| screen_time_hours | 0.003 |
| support_feeling | 0.001 |
| everything else | ~0.002 combined |

Mood carries **99%** of the model's decision. That has two consequences you
should be ready for:

- It is why the sleep what-if curve is nearly flat, and why the simulator
  *tells you* it is flat rather than pretending otherwise. This is the
  honesty check working, not a bug.
- `mood` and `stress_level` (the label) are close to the same underlying
  construct, so the model is closer to a tautology than the docstring's
  "behavioural predictor" claim suggests. The zero-false-negative confusion
  matrix row `[0, 830]` points the same way — it never misses a positive,
  which is unusual and consistent with a near-redundant feature.

If asked, the honest answer is: *"AUC 0.94 looks strong, but the feature
importances show mood doing 99% of the work, and mood is close to a restatement
of the stress label. I'd drop mood and re-measure before claiming it predicts
burnout from behaviour."* **That answer will earn you more credit than the
0.94 will.**

## B. The new What-If system

`ml/whatif_engine.py` (Engine D). One sentence: *take the existing model,
feed it a modified input, record what it said.*

### B1. The five steps

1. **Baseline** — run the existing `forecast_series()` on real, unmodified
   history. Reproduces exactly what the Analyse page shows.
2. **Lock the model** — every scenario is forecast with the *same* winning
   method. If one scenario used ARIMA and another XGBoost, part of the gap
   between them would be a model artifact, not an effect of the lever.
3. **Modify the input** — the lever multiplicatively rescales the historical
   series. Shape and trend (what the models learn from) are preserved; only
   the level moves.
4. **Re-predict** — through the same function. Because ARIMA and XGBoost are
   non-linear, the result is **not** just baseline × lever factor.
5. **Cache** — every grid point into `whatif_cache`, so sliders are instant
   and the live app still never calls Python at request time.

### B2. The levers

| Category | Lever | Grid | Mechanism | Predicted |
|---|---|---|---|---|
| Finance | Savings rate | 0–70%, step 5 | Expense history × `(1−r)/(1−r_now)`. Income never modified. | Savings next month (₹) |
| Habits | Check-ins/week | 0–7, step 0.5 | `days = completion_pct/100 × 7` — maps onto a real model input exactly | Completion % next week |
| Productivity | Focused hours/day | 0.5–6.0, step 0.5 | Only `time_pct` moves; score rebuilt with its own 0.6/0.4 formula | Productivity Score next week |

Habits and Productivity answer **different questions**: "I showed up on more
days" vs. "I worked longer on the days I showed up".

### B3. The burnout simulator — the strongest demo in the project

1. Load the **already-trained** `burnout_model.joblib`.
2. Read the feature vector Engine C **already computed** for you, from
   `burnout_predictions.payload['features_used']`.
3. Change **one value**.
4. Call `.predict_proba()`.

Nothing re-fitted, no feature re-derived. `burnout_model.py` isn't even
imported — its stored output is read instead, so this code physically cannot
change how Engine C behaves. Column order comes from `clf.feature_names_in_`.

### B4. How scenarios are chosen

EXPECTED = grid point nearest what you're actually doing. IMPROVED / RISK =
a fixed step either side, clamped to the grid. Deliberately *not* the best and
worst points — a scenario is only useful if it's a plausible change. When
you're already at an end of the slider, the UI says so instead of showing a
meaningless zero difference.

### B5. Two honesty checks

`response_summary()` flags, and the UI states plainly:

- **flat** — prediction barely responds to the lever (a real result:
  "something else is driving this")
- **non-monotonic** — response wobbles rather than moving steadily, because
  tree models predict in steps

### B6. Interpolation policy

**The slider only stops on values the model was actually run on.** A
prediction that was never made is never displayed.

### B7. Buy vs. Rent is NOT machine learning

`buy_vs_rent()` in `includes/whatif.php` — deliberately kept *out* of the ML
directory so the separation is structural, not just a comment. The
forecasting model was trained on monthly income/expense totals; it has never
seen a property price, a loan rate or a rent. It is a standard net-worth
comparison: buy side pays deposit + EMI + upkeep and ends with
`property value − outstanding loan`; rent side pays rising rent, invests the
deposit and the monthly difference, and ends with the portfolio. Every rate is
an assumption you set.

## C. Hugging Face

| | |
|---|---|
| Model | `meta-llama/Llama-3.1-8B-Instruct` (default; `HF_MODEL` in `.env` swaps it) |
| Endpoint | `https://router.huggingface.co/v1/chat/completions` (OpenAI-compatible, non-streaming) |
| Auth | `Authorization: Bearer $HF_API_KEY` |
| Params | `temperature 0.3`, `max_tokens 320`, `stream false` |
| Called from | `includes/ai_insight.php` ← `ai_insight.php` ← the "Generate insight" button |
| Receives | ~20 already-computed numbers |
| Returns | 3–5 sentences of prose |
| Cached in | `ai_insight_cache`, keyed by SHA-1 of the exact numbers sent |

### Why this model

- **Verified working** — tested end to end against the live router from this
  machine, returning real prose for all four categories
- **Free / low cost** — 8B, comfortably inside the free inference credits
- **Fast** — ~1s, and the UI blocks on it
- **Good at constrained prose** — follows "explain these, invent nothing"
- **Swappable** — one line in `.env`

**A reasoning model must NOT be used here**, and this was found the hard way.
`openai/gpt-oss-20b` was the original default. Reasoning models split their
output into a reasoning channel and a final answer, and at this task's small
token budget the budget goes entirely to reasoning — the call returns **HTTP
200 with empty content**, so the app silently fell back to its local writer.

Measured against the live router: `meta-llama/Llama-3.1-8B-Instruct` ✅ and
`deepseek-ai/DeepSeek-V3.2-Exp` ✅ return real prose; `openai/gpt-oss-20b` ❌
and `zai-org/GLM-4.5-Air` ❌ return empty content; `Qwen/Qwen2.5-7B-Instruct`,
`mistralai/Mistral-7B-Instruct-v0.3` and `google/gemma-2-2b-it` ❌ are not
served by any provider (HTTP 400).

The router also picks a provider for you and some are **region-blocked** —
Groq returned an HTTP 403 Cloudflare page from India during testing. The
parser now names both cases specifically (`reasoning_only: …`,
`bad_response: …`) instead of reporting a bare "empty".

A reasoning model buys nothing here anyway: the numbers are already final.

### It produces no numbers — three enforcement mechanisms

1. The **system prompt** forbids inventing, estimating, recomputing or
   rounding any number.
2. The **user prompt** writes every figure as literal text — *including the
   differences and percentage changes*, pre-computed by PHP — so there is
   nothing left to compute.
3. The **payload is tiny**: ~20 numbers. No raw transactions, check-ins or
   personal details leave the server. The UI shows the exact payload under
   "Exactly what was sent to the AI".

### Configuration — never hard-coded

`includes/env.php` reads, in order: real environment variable → `$_SERVER` /
`$_ENV` → the gitignored `.env`. `.env.example` is committed with key names
and no values.

```
HF_API_KEY=hf_…
HF_MODEL=openai/gpt-oss-20b
HF_API_URL=https://router.huggingface.co/v1/chat/completions
HF_TIMEOUT=20
```

### Fallback — tested against the running app, not assumed

| Failure | Result | `reason` |
|---|---|---|
| No API key | Local explanation | `no_api_key` |
| Invalid token | Local explanation | `auth: …` |
| Model unavailable | Local explanation | `model_unavailable: …` |
| Rate limited (429) | Local explanation | `rate_limit: …` |
| Network down/timeout | Local explanation | `network: …` |
| Empty response | Local explanation | `empty: …` |
| Cache table missing | Works, uncached | — |

In every case you keep predictions, simulations, comparisons and charts. Only
the paragraph changes source, badged **"📝 Written locally"** vs.
**"✨ Written by …"**.

The local writer is careful about three things: it distinguishes a
*backtest on your own history* from a *held-out split of a public dataset*;
it changes its wording when accuracy is below 60%; and it omits percentage
change when the baseline is zero rather than printing `+—%`.

## D. AI concepts actually used

Concepts this project does **not** use — neural networks, deep learning,
reinforcement learning, fine-tuning, RAG, vector databases — are deliberately
absent. Listing them would make the project sound more advanced than it is.

| Concept | Definition | Why we use it | Where |
|---|---|---|---|
| Machine Learning | Learning patterns from data instead of hand-written rules | Spending and habits are too messy for explicit rules | `forecasting.py`, `burnout_model.py` |
| Predictive Analytics | Using history to estimate what hasn't happened | The whole point of Forecast + What-If | `forecast_cache`, `whatif_cache` |
| Forecasting | Predictive analytics where the target is a future point in a time series | All four targets are ordered in time | `forecast_series()` |
| Regression | Predicting a continuous number | Rupees, percentages, a 0–100 score | `LinearRegression`, `XGBRegressor` |
| Classification | Predicting a category with a probability | Burnout is yes/no; probability is more useful | `RandomForestClassifier`, `.predict_proba()` |
| Time-Series Analysis | Exploiting the fact observations are ordered and self-correlated | Last month genuinely informs this month | `ARIMA(1,1,1)`, lag features |
| Data Preprocessing | Cleaning/reshaping before the model sees anything | Real exports have mixed date formats and duplicates | `load_kaggle_dataset()`, `clean_amount_outliers()` |
| Feature Engineering | Constructing input variables rather than using raw columns | Tree models have no built-in notion of time | lags + month index; the 9-feature wellness vector |
| What-If Analysis | Asking what a model would have predicted given a different input | A forecast says where you're heading; a what-if says which lever matters | `ml/whatif_engine.py` |
| Scenario Simulation | Running named alternatives through the same model | Three labelled cases beat a continuous curve | `pick_scenarios()` |
| Exploratory Data Analysis | Summarising/visualising before concluding | Makes a forecast interpretable | Analyse page charts |
| Correlation Analysis | How strongly two variables move together (−1…+1) | Shows which behaviours travel together, without claiming cause | `pearson_r()`, r under every scatter |
| Model Evaluation / Backtesting | Measuring error on data not fitted on | Without it, "the model predicts X" is unfalsifiable | `backtest_and_pick_best()` (MAE/RMSE/MAPE), accuracy + AUC |
| Confidence Intervals | A range expressing uncertainty, widening with distance | A single number implies precision a forecast lacks | `confidence_interval()` |
| Natural Language Processing | Computers working with human language | Prose is the natural form for an explanation | The HF layer |
| Large Language Models | Large text-trained models that write fluent prose | Great at explaining tables, bad at reliable numbers | `HF_MODEL` |
| Prompt Engineering | Writing instructions that constrain the output | Unconstrained, an LLM will happily invent numbers | `AI_SYSTEM_PROMPT` |
| API-Based AI Inference | Calling a hosted model over HTTP | A usable LLM won't run on a XAMPP box | `ai_call_huggingface()` |
| Recommendation Systems | Suggesting what to do next — here **knowledge-based**, not collaborative | One user means no crowd to collaborate with | Scenario ranking + AI explanation |
| Graceful Degradation | Failing to reduced capability, not breaking | The AI layer depends on a third party that will eventually fail | `ai_fallback_insight()` |

## G. Viva preparation

**What is What-If Analysis?**
Asking what the model *would have* predicted if one input had been different.
The forecast says where you're heading; the what-if says which lever is worth
pulling. I change the input, not the model.

**Why didn't you use Hugging Face for the numerical prediction?**
Because it would be guessing. An LLM has no access to my transaction history,
can't fit a trend to it, and can't tell me how wrong it's likely to be. My
forecasting models are backtested against my own real past periods, so every
prediction ships with a measured error and a confidence band. An LLM asked for
"next month's expenses" gives a number that *sounds* plausible with nothing
behind it — exactly the failure mode this architecture avoids.

**Difference between your ML model and the Hugging Face model?**
Different jobs. The ML models produce **every number** — they take numeric
series, output numeric predictions, and are scored by backtesting. The HF
model produces **no numbers at all** — it takes about twenty already-computed
figures and writes three to five sentences about them. One predicts; the
other explains.

**What is forecasting?**
Predictive analytics where the target is specifically a future point in a
time series, so the *order* of observations carries information. I use three
candidates — Linear Regression, ARIMA and XGBoost — and backtest to pick one.

**What is predictive analytics?**
Using historical data to estimate something that hasn't happened yet.

**What is scenario simulation?**
Running several concrete, named alternatives through the same model and
comparing the results. I use three — Expected, Improved, Risk — because three
labelled cases are far easier to act on than a continuous curve.

**How does your recommendation engine work?**
It's **knowledge-based**, not collaborative — with one user there's no crowd
to collaborate with. The simulator ranks the outcomes of each option using the
trained model, and the AI layer explains that ranking in words. The ranking is
ML; the wording is the LLM.

**Why did you use a Hugging Face model?**
Free/low-cost inference for open models over an OpenAI-compatible API, no GPU
and no local hosting, and the model is swappable with one line in `.env`. I
picked `openai/gpt-oss-20b` because it's served by several providers (so it's
unlikely to be unavailable mid-demo), it's fast enough that the UI can block
on it, and it follows a constrained "explain, don't calculate" prompt reliably.

**What data was used to train the ML model?**
Two different things. The burnout classifier was trained on a real external
dataset — 30,000 daily student check-ins. The forecasting models are fitted on
**my own** logged history at prediction time; a benchmark file only supplies
typical category proportions before I have enough of my own data, and that
benchmark is **synthetic**, generated with a fixed seed. A real Kaggle
transactions file is bundled as an alternative but isn't the default.

**Was the user's personal data used for training?**
No. The burnout classifier was trained entirely on the public dataset and is
then *applied* to my data. The forecasters are fitted on my own history at
prediction time — nothing is learned from me and stored for anyone else,
there's no shared model across accounts, and nothing I log is sent anywhere.
The only data leaving the server is the ~20 already-computed numbers handed
to the AI writer, and the app shows exactly what those were.

**How does the model handle new user data?**
Cold start is handled by blending. With no history at all, the finance page
shows the benchmark's category breakdown, clearly labelled as not mine. As I
log months, weight shifts linearly toward my own data and reaches 100% at six
months. For burnout, any feature the app never collects — screen time, social
interaction, felt support — is filled from the benchmark population average
and flagged as benchmark-filled, which is what the "data completeness %"
figure reports.

**How do you evaluate the model?**
Backtesting. I hold out the last few real periods, re-fit each candidate on
only the earlier data, and score predictions against what actually happened —
MAE, RMSE, MAPE and accuracy (100% − MAPE). The lowest-MAE model is the one
used, and the comparison table is shown in the UI rather than hidden. The
burnout classifier uses a stratified 80/20 split scored by accuracy and
ROC-AUC (0.854 / 0.942). Confidence bands come from the winning model's own
backtest RMSE, widening as √step.

**What happens if Hugging Face is unavailable?**
Nothing breaks. Predictions, simulations, scenario comparison and every chart
are all produced before the AI is ever called. A locally-written explanation
takes its place, built from the same numbers, and it's badged "Written
locally" so the difference is never hidden. I tested every failure path —
missing key, rejected token, unavailable model, rate limit, network failure,
empty response.

### Three questions you should be ready for

**"Your burnout model has AUC 0.94 — isn't that suspiciously high?"**
Yes, and I'd flag it myself. The feature importances show `mood` carrying 99%
of the decision, and mood is close to a restatement of the stress label the
model is trained to predict. The confusion matrix has zero false negatives,
which points the same way. I'd drop mood and re-measure before claiming it
predicts burnout from behaviour.

**"Why is the sleep slider flat?"**
Because the model barely uses sleep — 0.003 importance against mood's 0.990.
The simulator detects that and says so rather than drawing three
near-identical bars and implying a difference that isn't there. A flat
response is a real result.

**"Is your what-if just multiplying the forecast by the lever?"**
No. If the winning model is Linear Regression it's close to linear, but ARIMA
and XGBoost are non-linear, so rescaling the input series and re-forecasting
gives a genuinely different shape. That's why the response curve is plotted
across all 12–15 grid points instead of just drawing a straight line between
three.

## Fixed: stale demo data

**The problem.** The demo payload stores *absolute* dates and ended
2026-09-07, so the seeded data went stale a little more each day. Once the
newest data was more than a week old, the last **complete** week was empty and
ARIMA faithfully extrapolated that crash to a productivity forecast of
**0/100 at ~28% backtest accuracy**. The model was behaving correctly on stale
input — but it made every scenario comparison read as zero.

**The fix.** `ml/seed_demo_users.php` is now **date-relative**: it finds the
newest event in the payload and shifts every date forward by a constant offset
so that event lands on today. Re-running the seeder therefore always produces
current data.

**Why an exact shift rather than a multiple of 7.** Shifting by an arbitrary
number of days moves each event to a different weekday, which would scramble
any designed weekday pattern and make the "most productive day" analysis
meaningless. That was checked before choosing: check-ins per day are flat
across weekdays in this payload (persona 0: 3.15–3.54; persona 1: 1.19–1.81 —
noise, not structure), so there is no pattern to preserve, and an exact shift
is both safe and better, because it runs the data right up to today and keeps
streaks alive. A `$SHIFT_WHOLE_WEEKS` flag switches to week-aligned shifting
if the payload is ever regenerated with a real weekday pattern.

Goals' `created_at` is now also backdated to each goal's first check-in.
Previously every goal was created "now", so the Analyse page computed
"days active = 1" next to months of history and reported a nonsensical 100%
consistency.

**Result** (after re-running `train_model.py` → `burnout_model.py` →
`whatif_engine.py`, in that order):

| Metric | Before | After |
|---|---|---|
| Productivity baseline (Riya) | 0.0 /100 | **90.3 /100** |
| Productivity backtest accuracy | 28% | **98.8%** |
| Habit backtest accuracy | 25% | **97.4%** |
| Finance backtest accuracy | 94.1% | 84.2% |
| Longest live streak | broken | **20 days** |

The two personas now also demonstrate *both* burnout behaviours, which is
useful in a viva: Karan sits at **75% risk** with a sleep curve that responds
monotonically (9.5h → 73.3%, 6.5h → 75.8%), while Riya sits at **4.9%** with a
curve the simulator correctly flags as **flat**.

Note the finance accuracy *fell* slightly (94.1% → 84.2%). That is expected
and not a regression: the shift added a newer month to the series, and the
model is now being scored against a different, harder holdout. Both figures
are honest backtests of their own data.
